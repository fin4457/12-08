### Задание 1. Резервное копирование

### Кейс
Финансовая компания решила увеличить надёжность работы баз данных и их резервного копирования. 

Необходимо описать, какие варианты резервного копирования подходят в случаях: 

1.1. Необходимо восстанавливать данные в полном объёме за предыдущий день.

1.2. Необходимо восстанавливать данные за час до предполагаемой поломки.

1.3.* Возможен ли кейс, когда при поломке базы происходило моментальное переключение на работающую или починенную базу данных.

*Приведите ответ в свободной форме.*  

### Решение 1.  
1.1. Для восстановления данных в полном объеме за предыдущий день можно реализовать несколькими вариантами:  
 - Ежедневное полное копирование (Full Backup)  
  Каждый день в нерабочее время создается 100% копия всей базы данных. Преимущества в высокой скорости восстановления, но высокая нагрузка на сеть и СУБД во время копирования, а также требуется большой объем хранилища.  
- Полное + Дифференциальное копирование (Full + Differential)  
  Полный бэкап делается раз в неделю (воскресенье). Каждую следующую ночь делается дифференциальный бэкап, который собирает все изменения, произошедшие с момента воскресенья. Преимущества в быстрой скорости восстановления. Для восстановления за предыдущий день нужны всего два файла: воскресный полный и дифференциальный за нужный день. Экономит место в первые дни недели, нагрузка на СУБД ниже, чем при ежедневном полном бэкапе.  
- Полное + Инкрементальное копирование (Full + Incremental)
  Полный бэкап делается раз в неделю. Каждую ночь делается инкрементальный бэкап, который собирает изменения только за последние 24 часа (с момента вчерашней копии). Скорость восстановления низкая. Чтобы восстановиться, например, за четверг, СУБД должна последовательно применить полный бэкап воскресенья и цепочку инкрементальных бэкапов за понедельник, вторник, среду и четверг. Минимальная нагрузка на сеть и хранилище, копии создаются быстрее всего.

1.2. Для восстановления данных с точностью до часа до поломки можно применить Репликацию с задержкой.  
 Создается резервный сервер базы данных (Slave/Replica), на который данные с основного сервера передаются не мгновенно, а с фиксированной искусственной задержкой ровно в 1 час. Например если в 14:00 на основном сервере произошел критический сбой, то на резервном сервере в этот момент будут находиться чистые данные по состоянию на 13:00. Администратор останавливает репликацию и переводит пользователей на этот сервер. Восстановление происходит практически мгновенно, не нужно тратить время на разворачивание бэкапов из файлов.  

1.3. Такой кейс абсолютно возможен. Создаются как минимум два сервера СУБД — Основной (Primary/Master) и Резервный (Secondary/Slave). Данные между ними синхронизируются синхронно (в режиме реального времени). Каждая транзакция считается успешной, только когда она записалась на оба сервера. Специальный модуль-арбитр (кластерный менеджер) постоянно проверяет (Heartbeat) основного сервера. Если основной сервер отключается, арбитр за несколько секунд автоматически делает резервный сервер основным. Перед кластером стоит виртуальный IP-адрес (балансировщик). Клиентские приложения и пользователи не замечают сбоя — их запросы просто мгновенно перенаправляются на живой сервер.

### Задание 2. PostgreSQL

2.1. С помощью официальной документации приведите пример команды резервирования данных и восстановления БД (pgdump/pgrestore).

2.1.* Возможно ли автоматизировать этот процесс? Если да, то как?

*Приведите ответ в свободной форме.*  

### Решение 2.  

В PostgreSQL есть встроенный инструмент для создания резервных копий — утилита pg_dump.  

   `pg_dump <параметры> <имя базы> > <файл для сохранения копии>`  

Резервная копия создается следующей командой:  

   `pg_dump <имя базы> > /tmp/backup.dump`  

Если требуется авторизация под определенным пользователем, можно воспользоваться ключом -U:  

   `pg_dump -U <имя пользователя> -W <имя базы> > /tmp/backup.dump`  

Ключ -U определяет пользователя, а -W обязывает ввести пароль.  

Утилита pgrestore позволяет восстанавливать данные из резервных копий. Чтобы восстановить только определенную БД, нужно запустить эту утилиту с параметром -d  

   `pg_restore -d <имя базы> /tmp/backup.dump`  

Процесс можно полностью автоматизировать с помощью системных планировщиков задач, например через cron. Для автоматизации необходимо сделать автоматический ввод пароля и регулярный запуск скрипта по расписанию.  

1. Настраиваем автоматическую авторизацию
2. Создаем скрипт резервного копирования
3. Настраиваем расписание в Cron.

### Задание 3. MySQL

3.1. С помощью официальной документации приведите пример команды инкрементного резервного копирования базы данных MySQL. 

3.1.* В каких случаях использование реплики будет давать преимущество по сравнению с обычным резервным копированием?

*Приведите ответ в свободной форме.*

### Решение 2.  

Для создания инкрементного резервного копирования в MySQL используется утилита MySQL Enterprise Backup (команда mysqlbackup), которая входит в коммерческую версию СУБД
```
mysqlbackup \
  --defaults-file=/etc/my.cnf \
  --user=backup_user \
  --password='your_password' \
  --incremental \
  --incremental-base=history:last_backup \
  --incremental-backup-dir=/var/backup/incremental_data \
  backup
```
В бесплатной версии MySQL утилита mysqldump не поддерживает инкрементные бэкапы (она способна делать только полные логические дампы). Для организации инкрементного копирования применяется форк утилиты под названием mariadb-backup (ранее mariabackup) или Percona XtraBackup.

Percona XtraBackup 

Порядок действий:  
- Полная резервная копия. Создаётся согласованная копия базы. После этого в каталоге создаётся файл xtrabackup_checkpoints, который содержит LSN и служит основой для инкрементных копий.
- Первая инкрементная копия. Выполняется с указанием каталога полной копии через флаг --incremental-basedir. Утилита считывает LSN из xtrabackup_checkpoints и копирует только изменённые с этого момента страницы.
- Последующие инкрементные копии. Для каждой следующей копии в цепочке флаг --incremental-basedir указывает на непосредственно предшествующую инкрементную копию.  

```
# Полная резервная копия
xtrabackup --backup --user=root --password=secret --target-dir=/backups/full-2025 --datadir=/var/lib/mysql

# Первая инкрементная копия (опора на полную)
xtrabackup --backup --user=root --password=secret --target-dir=/backups/incr-1 --incremental-basedir=/backups/full-2025

# Последующая инкрементная копия (опора на предыдущий инкремент)
xtrabackup --backup --user=root --password=secret --target-dir=/backups/incr-2 --incremental-basedir=/backups/incr-1
```

Использование репликации вместо (или в дополнение) обычного резервного копирования дает ключевые преимущества в ситуациях, когда на первом месте стоят минимальное время простоя, сохранение последних данных и снижение нагрузки на основную базу.
